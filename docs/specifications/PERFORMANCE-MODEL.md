## The model

```
goodput ≈ N × (1 − O) × B × Rfec × Fd × (Pc + Pm) × H × Rfountain
```

| Symbol | Meaning | Units |
|---|---|---|
| `N` | Total logical cells per optical frame | cells |
| `O` | Non-payload cell fraction (markers, pilots, header, guards) | fraction |
| `B` | Raw bits per payload cell | bits |
| `Rfec` | Intra-frame FEC code rate | fraction |
| `Fd` | Distinct display states presented per second | states/s |
| `Pc` | Fraction of display states captured cleanly and decoded | fraction |
| `Pm` | Fraction of mixed states from which data is recovered | fraction |
| `H` | Header success probability | fraction |
| `Rfountain` | Fountain efficiency (payload ÷ delivered symbols) | fraction |

Intermediate quantities the script also reports, because they must never be confused with
goodput (ADR-0012):

- **Raw bit rate** = `N × (1−O) × B × Fd` — what the display emits.
- **Corrected bit rate** = raw × `Rfec × (Pc+Pm) × H` — after coding and losses.
- **Goodput** = corrected × `Rfountain` — the metric.

## ⚠ The variables are not independent

The model multiplies these as though they were independent. **They are not.** Known
couplings, all `[HYP]` until Phase 2 measurement:

| Coupling | Direction |
|---|---|
| `B ↑` | → `Rfec ↓`, `Pc ↓` (less noise margin per symbol) |
| `Fd ↑` | → `Pc ↓` (more display states per camera frame ⇒ more mixing) |
| `N ↑` | → `Pc ↓` (smaller cells ⇒ more crosstalk, more blur sensitivity) |
| `Rfec ↑` | → frame error rate ↑ (weaker code ⇒ more whole-frame losses ⇒ effective `Pc ↓`) |
| distance ↑ | → usable `N` ↓ **and** `Pc` ↓ together |

There is also a **density cliff the model does not contain at all.** ChromaCode's measured
cell-size sweep showed goodput rising 28 → 137 kbps as cells shrank, then **collapsing to
58 kbps** past a threshold. `[LIT]` Our model's grid sweep is monotonic; reality's is not.
The model is therefore only valid up to a density limit that EXP-001 must locate.

**This model must be replaced or corrected with measured channel data.** Its purpose is to
size the problem and identify which variables deserve attention — not to predict results.

## What the model says

### 1. Binary luminance at 60 states/s does not reach milestone 4

The best binary scenario — largest grid, most optimistic channel assumptions —
reaches **145 KB/s** against a 200 KB/s target. The expected case is **78 KB/s**.

**Milestone 4 requires either four-level modulation (M2) or `Fd` above 60.** This is the
single most important planning conclusion in the model, and it should shape the roadmap:
Phase 6 (multilevel modulation) is not an optional enhancement, it is on the critical path
to the headline target.

### 2. Milestone 5 (500 KB/s) needs mixed-frame recovery

No scenario at 60 display states/s reaches 500 KB/s. The only modelled scenario that does
is **M4 mixed-frame recovery at 120 states/s (576 KB/s)** — which depends on both the
high-frame-rate capture path (ADR-0005, unvalidated) and rolling-shutter unmixing
(Phase 7, research). Milestone 5 is therefore a genuine research target with two
independent unproven dependencies.

### 3. Milestone 6 (1 MB/s) is not reached by any modelled scenario

The most optimistic scenario modelled reaches 576 KB/s. Exceeding 1 MB/s would need
roughly double that — e.g. a larger grid *and* higher `Pm` *and* `Fd` above 120. The
charter correctly frames this as "investigate whether", and the model supports that
framing: **there is currently no credible path to 1 MB/s on the table.** Saying so now is
better than discovering it in Phase 8.

### 4. `Pc` is the highest-leverage variable we control indirectly

`B`, `Rfec`, `Fd` and `Pc` all show ~40% goodput swing for ±20% change. Of these:
- `B` is chosen (modulation mode)
- `Fd` is bounded by the platform
- `Rfec` is chosen, but constrained by error rate
- **`Pc` is earned** — through exposure control, focus lock, tracking quality, phase
  classification and frame-drop avoidance

`Pc` is where systems engineering pays off most, and it is the variable most likely to be
worse than assumed in the field. Every scenario above assumes `Pc` between 0.55 and 0.80,
which is **completely unvalidated**.

### 5. `O` barely matters

Frame overhead shows only ~7% swing. This is important for the frame-layout decision:
**candidate layouts should not be selected on overhead.** A layout costing 10% more cells
that raises `Pc` by 15% wins comfortably. See
[OPTICAL-FRAME-CANDIDATES.md](OPTICAL-FRAME-CANDIDATES.md#comparison).

### 6. Raw rate is a poor proxy — as the literature confirms

The M4 scenario emits **7.30 Mb/s raw** and delivers **576 KB/s (4.6 Mb/s) goodput** — a
1.6× gap under *favourable* assumptions. ChromaCode measured a 6.5× gap in practice, and
saw goodput fall ~119× while raw rate fell only ~6× under degradation. `[LIT]` Our model's
gap is optimistic because it assumes the channel behaves as modelled.

## Parameter provenance

Every parameter below is a **starting hypothesis requiring validation**. None is measured.

| Parameter | Value range used | Basis | Validated by |
|---|---|---|---|
| `N` | 15,360 / 24,000 / 34,560 | Charter's candidate grids | EXP-001, EXP-013 |
| `O` | 0.12–0.20 | Estimated from the three candidate frame layouts | EXP-013 |
| `B` | 1 or 2 | Modulation mode definition | — |
| `Rfec` | 0.65–0.85 | Typical code rates; lower for higher-order modulation | EXP-011 |
| `Fd` | 30 / 60 / 120 | Panel capability; **assumes requested states are actually presented** | EXP-006 |
| `Pc` | 0.55–0.80 | **Guess.** Genuinely unknown; the weakest input in the model | EXP-008, EXP-009 |
| `Pm` | 0.0 or 0.30 | **Guess** for M4 recovery rate | Phase 7 |
| `H` | 0.95–0.99 | Assumes heavy header protection works | EXP-013 |
| `Rfountain` | 0.90–0.97 | RaptorQ-class overhead is low; LT-class is worse | EXP-012 |

**`H` and `Rfountain` against what has since been measured (2026-10-23)** — recorded here, not
retuned into the script, per the rule below:

- **`H`: real optics read 0.026–0.378** (F36, F45), one rig, against an assumed 0.95–0.99. The
  single largest gap between this model and reality so far. F45–F48 and F50 target it; no capture
  since has measured the effect.
- **`Rfountain`: the v1 implementation was below the assumed range** — ~0.75–0.83 at 5–30% frame
  loss (F49), simulated. Protocol v2 measures **0.98–1.00** in the same simulation, now above it.
  The range above was right about what a good fountain code gives and wrong about the code we had.

**`Pc` deserves emphasis.** It is a guess, it is one of the highest-leverage variables, and
it multiplies through every scenario. If real `Pc` is 0.35 rather than 0.70, every number
above halves and milestone 4 becomes unreachable even with M2. Measuring `Pc` early is more
valuable than any optimisation.

## How this model gets replaced

| Phase | Replacement step |
|---|---|
| Phase 1 | Simulator produces `Rfec`, `Rfountain`, `H` under modelled impairments — replacing three guesses with simulator outputs (still `[HYP]`) |
| Phase 2 | **Channel characterisation measures `Pc`, `Fd` and the density cliff on real hardware.** This is the model's moment of truth |
| Phase 3+ | Measured end-to-end goodput compared against model prediction; the gap is reported as a number and the model corrected |
| Phase 5 | Model retired as a planning tool, retained only as a historical record of what we expected |

When measurements arrive, **update the script, regenerate, and record both the old and new
predictions.** Do not quietly retune parameters to match results — a model tuned after the
fact predicts nothing, and the difference between predicted and measured is itself the most
valuable output.
